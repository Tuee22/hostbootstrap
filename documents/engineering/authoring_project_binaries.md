# Authoring A Project Binary

**Status**: Supporting reference
**Supersedes**: N/A
**Referenced by**: [documents-index](../README.md), [composition_methodology](../architecture/composition_methodology.md), [binary_context_config](../architecture/binary_context_config.md), [derived_project_standards](derived_project_standards.md)

> **Purpose**: A step-by-step guide for a new consumer — author the project's ordered step contribution
> finalized into its opaque `StepPlan`, supply the step actions, test suite, artifacts, and
> Dhall vocabulary, and declare the budget — extending `hostbootstrap-core` through the `Step` algebra.

## TL;DR

- **The plan is the project.** A consumer's primary contribution is an ordered additive step fragment,
  plus the actions for any project-specific `Step` kinds it adds. Finalization validates an opaque
  `StepPlan`, which exact plan admission turns into the current-frame input to `project up`. The consumer extends the plan and step
  vocabulary; the command surface (`project`, `test`, `service`, `context`, `check-code`) is fixed. The
  foundational model is [composition_methodology](../architecture/composition_methodology.md); the
  reusable shapes are [composition_patterns](composition_patterns.md).
- **`.dhall` is parameters + context + witness, never shape.** The root `<project>.dhall` carries the
  resource budget, the Dockerfile path, the deploy settings, the binary context, and its witnesses; the
  chain is a pure function of those parameters. Each frame's binary verifies it is in the frame its
  sibling `.dhall` describes, or fails fast before side effects.
- **The `Step` algebra is the reuse unit.** Core ships host-management step kinds; the project
  contributes its own step kinds into the same `[Step]`, and host and workload steps interleave freely.
  This is the workload-extension seam.
- **Frame** on this page is the topology sense of the [glossary](../README.md#glossary): one process's
  place in the lift stack (the metal host orchestrator, the VM, the project container).

## Steps

1. **Define the root config and budget.** The project binary owns `<project>.dhall`: the resource budget,
   the Dockerfile path, the deploy settings, any project-extended field (the demo's `message`), and the
   parameters the chain reads. `project init` writes the root `<project>.dhall` (a host-orchestrator config
   with no parent) by passing the parsed flags to
   `psAssemble (ProductionAssembly args)`. Core ships no default config values, so the resulting complete
   value and all defaults are entirely the project's. The binary owns three installed identities beside
   its executable: the handoff key pair (`<executable>.handoff.key`, `<executable>.handoff.pub`), the
   separate build-signing key (`<executable>.build.key`), and the activation key pair
   (`<executable>.activation.key`, `<executable>.activation.pub`). Two entries install or validate all
   five files: the private `--hostbootstrap-install-identity` entry, which Python's build invokes on the
   installed binary immediately after every build, and a successful root `project init` at the
   executable's real sibling path. Existing valid keys survive `--force` and rebuilds; an orphaned public
   key, malformed key, or mismatched pair refuses instead of rotating identity, so an identity refusal can
   surface at the end of a build as well as at `project init`. Child-role init, `service init`, and
   arbitrary `--output` paths cannot mint root secrets (see
   [binary_context_config](../architecture/binary_context_config.md#context-creation-is-internal-lifecycle-work-not-a-verb)).
   Python builds the binary, invokes that entry, and hands off to
   it (POSIX `exec`; Windows child subprocess); it does not initialize or trigger config creation, so a
   normal command fails fast (exit 1) until the
   executable-sibling config exists (written by `project init` or generated by the harness). Python
   discovers the Cabal-file stem and executable stanza separately, reads no Dhall, and implements no
   cryptography: it only invokes the binary's entry. See
   [schema](schema.md) and
   [resource_budgeting](resource_budgeting.md).
2. **Author the plan fragments.** Provide one or more
   `CanonicalProjectRoot scope rootId -> cfg scope -> [Step]` contributions with `addSteps`. The shared
   `scope` is part of the contract: a Production config cannot be paired with a Harness root, or with a
   different Harness run's root.
   `Step`/`StepKind` constructors are hidden, and Production `project up --dry-run` renders the exact
   admitted `ProjectPlan` whose forward projection the interpreter consumes. Validation rejects
   empty/duplicate/conflicting plans,
   noncontiguous `A/B/A` frames, and invalid post-handoff placement before effects; the complete set of
   refusals is the `StepPlanError` table in
   [run_models § Single-Representation Rule](../architecture/run_models.md#single-representation-rule). Frame-context and
   reverse behavior are carried by the plan's own steps; there is no separate lifecycle slot beside the
   plan. A step declares its frame descent with `descendsVia` and the effect that releases what it acquired
   with `reversedBy`; `mkStepPlan` refuses a `reversedBy` on a step whose `ReversePolicy` is
   `PreserveOnReverse`, and a step that acquires nothing declares no reverse effect. Compose from
   the core's host-management step kinds (`ensureStep`, `deployVMStep`, `copySourceStep`, `buildPbStep`,
   `buildImageStep`, `contextInitStep`, `deployKindStep`, `deployChartStep`, `exposePortStep`,
   `postHandoffStep`) and the project's own kinds via `projectStep`;
   host and workload steps interleave in one list. Core interprets the authorized current-frame segment;
   authenticated child entry uses the root catalog and storeless executor. Convenience IO actions report completion only; managed adapters provide exact settlement observations. See
   [composition_patterns](composition_patterns.md).
3. **Define project step kinds and their actions, then finalize the builder.** A workload step the core
   does not ship (deploy-registry, push-image, …) is a project-contributed `Step` kind built with
   `projectStep`, plus its action. `projectStep` takes a validated `ProjectStepId` and an explicit
   `ReversePolicy`. `projectStepId` accepts only a non-empty stable token (letters, digits, `-`, `_`, `.`)
   and returns `Left` otherwise. The policy is one of three:

   | `ReversePolicy` | Reverse behavior |
   |---|---|
   | `PreserveOnReverse` | the step enters no reverse projection and may not declare `reversedBy` |
   | `ProjectManagedReverse` | the step's own `reversedBy` effect, if any, releases what it acquired |
   | `CoreManagedReverse` | a core adapter releases it; a `reversedBy` on the step takes precedence |

   The demo's `demoProjectStep` wraps `projectStepId` and fixes `ProjectManagedReverse`; its provider-ensure
   row uses `projectStep` directly with `PreserveOnReverse`. Build the opaque spec through
   `ProjectSpecBuilder`:

   - `projectSpec` starts the builder from the non-empty `TestSuite`, the `check-code` action, the
     `ConfigArtifact` delta, the test-config codec, the `test init` builder, and the restricted assembler;
   - `addSteps` appends each ordered step fragment;
   - `addServices` appends each typed service registry (the service stream; finalization refuses duplicate
     identities);
   - `addAssemblyInputs` declares every read-only file the assembler may read. The assembler's restricted
     effect permits only declared reads, so an assembler that reads no file declares none (as the demo
     does), and a duplicate path refuses finalization;
   - `addForwardChildPlan` installs the one forward-child projector. It is a required single-assignment
     seam: given the current config, the parent and child frame identifiers, and the lift the parent
     supplies, it projects the exact next child's config and independently rebuilds that child's complete
     child-local `StepPlan`, returning the child's source root, config, and plan or a refusal. Core calls
     it on the current frame's one-layer forward topology edge to build the child it hands off to. The
     demo's projector is `demoForwardChildPlan`.

   `finalizeProjectSpec` returns `Left MissingStepPlan` without a step fragment, `Left MissingForwardChildPlan`
   without a projector, and `Left DuplicateForwardChildPlan` when `addForwardChildPlan` ran more than once.
   Pass only the opaque `Right` result to `runHostBootstrapCLI` so the contributions merge into the
   recursive interpreter. The core command surface (`project`/`test`/`service`/`context`/`check-code`) is fixed; the project
   extends the chain and the step vocabulary (the lift-chain stream of the extension-stream contract; see
   [library_hierarchy](../architecture/library_hierarchy.md)). The resulting `ProjectSpec cfg tcfg` does
   not name an installed-identity marker. At dispatch, `runHostBootstrapCLI` verifies its declared name
   against the actual executable basename before ordinary command parsing and retains the resulting generative identity through codec,
   service, plan, command, and Harness construction.
4. **Declare the boundaries the interpreter crosses.** Each descent is fractal bootstrap: provision the frame, build
   or install the binary in it, then hand the `project up` work off into the next frame. The consumer
   declares each boundary on the step that owns it with `Step.descendsVia`; that one `LiftContext` names the
   provider route (the selected VM provider into the VM, then a local `docker run` into the container) and
   carries the child config. The exact Production root invocation retains one plan through its
   current-frame Chain segment and selects the exact child from its rooted catalog. It launches the
   child binary through the lifecycle process route with the fixed private `--hostbootstrap-lifecycle-child`
   marker; the verb, plan, frame, and config travel in the authenticated Offer, not on the child's command
   line. The child is a storeless executor of root-granted nodes, and the root settles every result; the
   protocol is owned by [the recursive-lifecycle-command phase](../../DEVELOPMENT_PLAN/phase-17-recursive-lifecycle-command.md). See
   [`HostBootstrap.Lift`](../architecture/hostbootstrap_core_library.md) and
   [composition_methodology § Single Representation](../architecture/composition_methodology.md#single-representation-the-chain-is-the-representation).
5. **Supply the test suite.** Provide a `TestSuite`/`Case` matrix (the test stream); the intended
   operator entry is `test run <case-id>|all` from the root frame, gated on an existing
   `<project>.test.dhall` and refusing a pre-existing foreign `<project>.dhall`. Entry validates the root
   restriction before effects. A suite may declare more than one config variant; for each, the harness **generates**
   the run's `<project>.dhall` functionally via the Harness request of the same restricted `psAssemble`,
   under fresh exact-run authority and its matching mapped codec. It never shells the CLI: it retains the
   exact Harness plan, drives the hidden fixed root-Up entry into the common current-frame Chain, asserts the real workload in-frame, and
   always invokes the matching reverse projection and then the suite's post-reverse assertion before the
   next variant, whether the variant passes or an in-process failure is caught. Only a safety refusal
   proven to precede acquisition skips the reverse, because nothing has been acquired. A hard
   interruption does not run `finally`; the recovery sweep reopens the incomplete run before a new
   variant. The demo runs
   two variants whose only difference is `message`, and its Playwright `e2e-tabs` spec is polymorphic: it
   reads `EXPECTED_MESSAGE` and asserts whichever message the active deployment set. It reuses the chain
   rather than a separate per-case cluster. Each run owns its generated config and `.test_data/<runId>`
   root under exact Harness authority. Provider, cluster, and mount consumers project their inputs from
   that exact plan, as implemented by the
   [worked demo phase](../../DEVELOPMENT_PLAN/phase-24-worked-demo.md). See
   [testing](testing.md) and [harness_workflow](../architecture/harness_workflow.md).
6. **Register schema artifacts and Dhall vocabulary.** Pass only the project's `ConfigArtifact` delta
   to `projectSpec`; core concatenates `coreArtifacts` exactly once. `artifactOf` constructs an opaque
   `ConfigArtifact` from an admitted codec witness and canonical value; callers cannot pair unrelated
   schema/render text through a public constructor. Embed `Core.dhall` for any new step parameters, provider kinds, or witness
   kinds the chain introduces. In the current demo `contextInitStep`'s action body only announces its
   frame anchor, while the descent it declares carries the container payload; composite bootstrap, that
   declared descent plus the handoff, and deployment actions perform child projection/delivery. The exact
   plan node binds the projector and authenticated descent. See
   [config_generation](config_generation.md) and
   [dhall_topology](dhall_topology.md).

## A Worked Chain (the demo)

The demo's
`demoChainFor :: Substrate -> CanonicalProjectRoot scope rootId -> ProjectConfig scope -> [Step]` (in
`demo/src/HostBootstrapDemo/Commands.hs`) is the canonical example. Its default VM-backed branch nests
*pristine-host VM bootstrap* over *in-container deploy*, and every host and workload step lives in one
ordered `[Step]` spanning three frames:

```text
ensure-vm-provider host-orchestrator-0 (metal)     -- project step, preserve-on-reverse: ensure the VM provider (Incus on Linux, Lima on Apple, WSL2 on Windows)
deploy-vm       host-orchestrator-0 (metal)        -- launch/start the provider VM (creation-time wall; WSL CPU/memory is global)
build-pb        host-orchestrator-0 (metal)        -- pristine-bootstrap: build the binary host-native (#2) + the project image (#3) in the VM
copy-source     host-orchestrator-0 (metal)        -- attach the durable source to the VM; declares the metal-to-VM descent
context-init    vm-orchestrator-1 (vm)             -- announcing frame anchor; declares the container descent carrying the projected child config
deploy-kind     vm-project-container-2 (container) -- bring up the persistent kind cluster (cordon #2, config-selected run profile)
deploy-object-store    vm-project-container-2 (container) -- install the S3 store and create the registry's bucket
deploy-registry vm-project-container-2 (container) -- install the in-cluster registry and settle its runtime exposure
push-image      vm-project-container-2 (container) -- load the project image into kind and push it to the in-cluster registry
deploy-chart    vm-project-container-2 (container) -- apply the exact projected ConfigMap, then deploy the web pod
expose-port     vm-project-container-2 (container) -- verify the exact resolved web exposure is reachable
accelerator     selected frame                     -- after ingress: host post-handoff daemon on Apple Silicon/Windows GPU, in-cluster daemon on Linux CPU; absent on Windows CPU
```

The first metal row is the demo's own `ensure-vm-provider` project step (`projectStep` with
`PreserveOnReverse`), not a core `deployVMStep`: it calls `runEnsure` for the selected provider and enters
no reverse projection, so `project down`/`destroy` never uninstall the provider. The metal binary's
`buildPbStep` runs `pristine-bootstrap`: it stages the source into the VM, builds the
demo binary host-native (build #2), and builds the project image FROM the published base (build #3), all
in the VM. The metal segment's last row, `copySourceStep`, attaches the exact writable durable source to the
VM; it is the node that declares the metal-to-VM descent with `descendsVia`, and its `reversedBy` effect
releases the guest alias. The descent `contextInitStep` declares carries the project-container child
`<project>.dhall`, the handoff streams it, and that step's action body only announces the boundary. The container steps
stand up the persistent stack: `deployKindStep` brings up the cordoned kind cluster on the VM's Docker,
the deploy-object-store step establishes registry backing, and the deploy-registry and push-image steps
are the demo's own workload kinds in the same list (each built with `demoProjectStep`),
`deployChartStep` applies the binary-rendered child config and deploys the web pod; the exact mounted
bytes carry `message` and are rollout-hashed (the `serveWeb` handler reads them and the SPA renders `message` into
`#message`), and `exposePortStep` verifies the endpoint. Only after that ingress is reachable does the
selected accelerator step run: a metal-frame `postHandoffStep` on Apple Silicon and Windows GPU, or a
container-frame `deploy-accelerator-daemon` project step on Linux CPU (and on the direct Linux GPU lane).
The Windows CPU branch is the VM-backed stack alone, with no accelerator step. `project up` ends at a live
webservice on its exact runtime-resolved loopback endpoint with the selected accelerator placement, if any. The interpreter runs the steps in order; its
prepared managed adapters retain exact restart and settlement evidence.

`project down`/`destroy` retain or reconstruct the same exact Production plan. Their root entry joins the
pure reverse projection to exact command, journal, snapshot, lease, and receipt evidence, then drives
child-first authenticated teardown before stopping or deleting the provider. Neither the demo's host-backed
`.data` path itself nor any workload subtree under it enters a removal set; `project destroy` removes only
the plan-owned `cluster/<driver>/state` leaf beneath it. The worked-demo and substrate acceptance gates record the durable
readback they exercise. See [durable_state](../architecture/durable_state.md) and
[lifecycle state model](../architecture/lifecycle_state_model.md).

## Sketches

- **Managed cloud cluster**: a chain of `build-image → context-init → cloud-CLI create cluster (external
  state backend) → deploy-chart`. No deploy-vm step; the cloud is the substrate, expressed as project step
  kinds over the same `[Step]`.
- **Local cluster via a host service manager**: `ensure the cluster as a host service (rke2/k3s) →
  deploy-chart → optionally a cloud-validation step backed by an in-cluster state store`.
- **Daemon-backed accelerator**: `deploy web service → expose accelerator ingress → start in-cluster or
  host daemon → dispatch CBOR work to a generated worker`. The demo's implemented accelerator extension
  uses this shape for Swift/Metal, CUDA, and C++ add workers. Integration tests build the real worker, and
  the browser e2e proves the UI result came from daemon metadata; live closure remains substrate-specific.

Both are the same algebra — a `[Step]` chain interpreted recursively across a context topology — differing
only in which steps the chain selects. The chain is a pure function of the root parameters, so structural
variation lives in which steps it emits. The fail-fast frame check is applied at every boundary; cluster
teardown never removes the plan's `.data` path itself or a workload subtree under it, and Delete removes
only the plan-owned `cluster/<driver>/state` leaf beneath that path (see
[durable_state § Teardown guarantee](../architecture/durable_state.md#teardown-guarantee)).

## Current Status

`hostbootstrap-core` exposes exactly `project`, `test`, `service`, `context`, and `check-code`. The
consumer's contribution is additive root-bound `CanonicalProjectRoot -> cfg -> [Step]` fragments plus
project step actions; the demo supplies
`demoChainFor :: Substrate -> CanonicalProjectRoot scope rootId -> ProjectConfig scope -> [Step]`
in `demo/src/HostBootstrapDemo/Commands.hs`, wired into the builder with `addSteps` and
`finalizeProjectSpec`.
Production `project up` admits or reconstructs one exact plan and uses it for dry rendering and snapshot
persistence, then admits the root-refined lifecycle context and enters the Cabal-private root-Up
`LifecycleEntry` producer. That producer derives the journal/current cursor, calls generic
`authorizeRootProject`, and invokes the fixed current-frame Chain interpreter without exposing those raw
inputs to dispatch.
`down`/`destroy` use the same exact plan representation for authenticated recursive reverse work. Nested
entry verifies the root-selected catalog edge and grant before effects. Harness retains and interprets its
exact plan through the same boundaries, and demo profile/root consumers use exact-plan projection. The read-only `context` introspection
(`inspect`/`path`/`show`/`schema`/`render`, where `inspect` renders the lift composition with the current
frame marked), and the `test init` / `test run <case-id>|all` split are implemented. Current live
validation and closure belong in the development plan. The surface is fixed —
`project` / `test` / `service` / `context` / `check-code` — so the demo
adds no verbs: it contributes internal typed `web`/`accelerator` role definitions through `addServices`
(run by positional-argument-free `service run`; the build-time bridge that
generates the PureScript types folds into the project-image build, inside `build-pb` on the VM-backed
lanes and inside `build-image` on the direct Linux GPU lane) and its VM/provider IO as chain steps.
Core classifies a closed set of private argument vectors before the fixed parser (identity installation,
the lifecycle child, the frame child, and two more); they are absent from `--help` and a project needs
nothing to receive them. A project adds no pre-parser entry of its own
([development_plan_standards § P](../../DEVELOPMENT_PLAN/development_plan_standards.md#p-fixed-command-surface-and-the-extension-streams)):
a lane that retains a cluster releases it through the authenticated reverse child's core-managed reverse
in that cluster's frame. The demo departs from that contract today: its `main` intercepts
`--hostbootstrap-direct-cluster-release-v1 PROFILE` before `runHostBootstrapCLI` and routes it to
`runDirectClusterReleaseChild`, which releases the retained direct (nvkind) cluster from inside the project
image. Moving the direct lane onto the core-managed reverse and deleting that entry is owed by
[the worked demo phase](../../DEVELOPMENT_PLAN/phase-24-worked-demo.md). The core list is canonical in
[hostbootstrap_core_library § Entries before the parser](../architecture/hostbootstrap_core_library.md#entries-before-the-parser).
`ensure` is a reconciler library; core exposes `ensureStep`, but the demo does not use it. It ensures the VM
provider in its own `ensure-vm-provider` project row and calls `runEnsure` for Docker, CUDA, Apple Metal,
and Windows CUDA inside the direct lane's composite actions and the host accelerator daemon's worker
build. The forward-representation doctrine holds:
`demoChainFor substrate` produces one forward plan definition, and `test run all` admits that definition
under an exact Harness scope and drives the hidden fixed root-Up entry into the common current-frame Chain rather than standing up a
separate per-case deployment graph.

Under
[development_plan_standards.md § BB](../../DEVELOPMENT_PLAN/development_plan_standards.md) a project supplies
the generic `ProjectSpec cfg tcfg` seams — one identity-polymorphic restricted `psAssemble`, separate
`psTestInit`, a typed `ServiceRegistry cfg` whose projections work at every selected scope, and exactly one
forward-child projector installed with `addForwardChildPlan` (Step 3). Each frame's lift context
is not one of those seams: it is declared on the plan node that owns the boundary. There is no separate
teardown seam: each reverse effect is attached to its acquiring step with `reversedBy`, and a step fragment
receives the opaque `CanonicalProjectRoot`, so a direct-host reverse effect derives its paths from that root
rather than from descriptive `sourceRoot`. The demo's assembler carries its own defaults, including `message =
"Hello, world!"`, on the demo's OWN scope-indexed config family — core owns no project-specific field and
no generic extra slot. Production init and Harness generation structurally share that assembler; the
Harness request selects the variant message (including `"Hello, Universe!"` on the second run).
Service projection consumes explicit assembled Web ports and accelerator timeout, preserves both through
child projection, and invents no fallback values. See the
[generic_project_model.md](../architecture/generic_project_model.md) design,
[Dhall configuration and project model phase](../../DEVELOPMENT_PLAN/phase-7-dhall-configuration-and-project-model.md), and
[development_plan_standards.md § BB](../../DEVELOPMENT_PLAN/development_plan_standards.md).
