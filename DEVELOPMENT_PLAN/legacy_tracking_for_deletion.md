# Legacy Code Tracked For Deletion

**Status**: Non-normative
**Supersedes**: N/A
**Referenced by**: [development_plan_standards.md](development_plan_standards.md)

> **Purpose**: Name the code that is still standing in the tree which the architecture does not want, and
> the phase whose completion deletes each piece.

This document is **not normative** and it is **not a work queue**. It schedules nothing: the deleting
phase's own `Remaining Work` is where that work is stated, and this table only records what is still
present in the meantime. It exists because § I distinguishes two different things:

- an **absence guard** asserts that a wrong shape is *gone* and cannot return — a test or validator
  check, never a document;
- this ledger records a shape that is *still here*, together with who removes it.

A phase's Objective and Deliverables never describe any of these shapes: under § D a phase says what it
builds, in present tense, and a surface the architecture does not want is one no phase builds. The deleting
phase's `Remaining Work` is the one place in a phase file that names the shape, as the deletion it owes.
Keeping the two apart is what stops this file from becoming the repair log § A forbids.

Every row names a **deleting phase** in its `Deleted by` cell, and the documentation validator refuses a
row whose cell does not hold exactly one link to a phase document that exists — an unowned row is exactly
how a ledger rots. The cell also names the Active or Planned sprint whose `Remaining Work` states the
deletion. A row is removed when its shape is. **An empty table is the healthy end state**, not a document
to keep populated.
