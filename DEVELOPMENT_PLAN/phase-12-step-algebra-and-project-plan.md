# Phase 12 — The step algebra and the single project plan

**Status**: Done
**Depends on**: Phase 5 (installed identity, operator verification, and authority kernels), Phase 7
(Dhall configuration and the generic project model), Phase 8 (ensure reconcilers and the generic Lift),
Phase 9 (lifecycle modes and run leases), Phase 11 (prepared operations)
**Substrates**: linux-cpu
**Gate**: `cabal test all` from `core/`
**Gate kind**: self-verifying
**Gate evidence**: 2026-11-01 ; x86_64 Linux, GHC 9.12.4, Cabal 3.16.1.0 ; `cabal test all` from `core/` ; pass ; covers in-gate

> **Purpose**: Admit a project's authored nodes into one scope-, specification-, plan-, and
> configuration-indexed value whose forward order, topology, stable snapshot, and reverse effects are
> projections of the same validated graph.

## Phase Objective

A project authors one identity-parametric `ProjectSpec cfg tcfg`. Scope finalization joins that static
specification to its exact project codec and service registry and yields
`FinalizedProjectSpec scope specDigest cfg`. The finalized value projects `PlanDraft` nodes from one
validated configuration and one canonical project root. `withProjectPlan` admits the resulting non-empty
draft stream under an exact lifecycle profile and yields a generative
`ProjectPlan scope specDigest planId configId cfg`. Every step presented to an interpreter, every topology
edge, every stable snapshot byte, every frame witness, every planned resource, and every reverse effect is
projected from that value.

The plan identity is local and generative; the persisted plan digest is stable and content-derived. The
public `StablePlanSnapshot` is a non-authorizing byte view, while the hidden kernel retains an indexed
companion for protected persistence. The snapshot boundary joins stable and local identities explicitly
through `BoundPlanSnapshot` and `PlanDigestBinding`. The Open branch of existing-snapshot admission,
recovery-profile opening, and reconstruction retain the one `planId` generated by that admission. A
terminal Production acknowledgment instead yields only its stable close key and generates no plan identity.
The context boundary similarly joins descriptive binary context to the exact plan through the pure
`CurrentFrame` admission. These evidence values make cross-scope, cross-configuration, cross-plan,
cross-digest, and cross-frame composition fail at the type boundary.

## Module Surface

`HostBootstrap.Lifecycle.Plan` is a hidden representation kernel. It owns internal node definitions,
validation, canonical encoding, and the constructors for plan-local evidence. It stays in Cabal's
`other-modules` and imports only lower-level plan vocabulary.

The Cabal-private `lifecycle-representation-internal` unit owns the primitive snapshot representations
and generic carrier/runtime state in `Lifecycle.Snapshot.Core` and `Lifecycle.Execution.Core`. Main and
both test components depend on that one compiled identity. Main specializes the payload and gate to its
own runtime-dependency package and prepared gate, and retains registry/service/gate policy.

The public surface is split into one pure facade and three evidence leaves:

- `HostBootstrap.ProjectPlan` exposes the opaque plan vocabulary and pure projections.
- `HostBootstrap.ProjectPlan.Construct` owns the scope-finalized specification wrapper and joins profiles,
  roots, validated configuration, and drafts.
- `HostBootstrap.ProjectPlan.Snapshot` joins a plan to the
  [lifecycle-modes-and-run-leases phase](phase-9-lifecycle-modes-and-run-leases.md)'s protected snapshot and
  lease transitions.
- `HostBootstrap.ProjectPlan.Frame` joins a plan to the
  [Dhall-configuration-and-generic-project-model phase](phase-7-dhall-configuration-and-project-model.md)'s
  descriptive binary context.
- `HostBootstrap.Authority.ProjectPlan` joins those pure plan projections to the matching protected snapshot,
  lease, journal, and live frame cursor before invoking the lower one-use reservation kernel.

`HostBootstrap.CLI` retains the static `ProjectSpec cfg tcfg` authoring surface. Its scope-finalization
function passes the static plan builder, static service registry, forward-child projector
(`psForwardChildPlan`; the bare binary passes `refuseForwardChildPlan`), and scope-correct codec to the lower
finalizer; the lower module therefore does not import `HostBootstrap.CLI`.

The dependency direction is:

```text
HostBootstrap.Lifecycle.Plan
    ↓
HostBootstrap.ProjectPlan
    ↓
HostBootstrap.ProjectPlan.Construct
HostBootstrap.ProjectPlan.Snapshot
HostBootstrap.ProjectPlan.Frame
    ↓
CLI scope finalization / lifecycle journal / Authority
    ↓
HostBootstrap.Authority.ProjectPlan
    ↓
Command / Chain / Reconcile / Teardown / resource consumers
```

The hidden kernel imports neither lifecycle mode, command authority, reconciliation, command dispatch, nor
teardown modules. `HostBootstrap.Lifecycle.Mode` may consume the kernel's private indexed snapshot companion
through its restricted internal import, while the snapshot leaf composes those protected primitives above
both modules. `HostBootstrap.Step`, `HostBootstrap.ProjectPlan`, and the hidden kernel import only Phase 7's
pure `HostBootstrap.Lift.Context` vocabulary. `HostBootstrap.Chain` may consume Phase 8's full generic
`HostBootstrap.Lift`, because it is the lower execution fold; plan-aware descent remains above the public
plan facade.

```haskell

data PlannedStep scope planId configId config

data ValidatedContext scope planId frame
data PlanDigestBinding scope specDigest planDigest planId

data BoundInvocationRecovery scope specDigest planDigest planId brokerGeneration

data AcquisitionJournal scope planId brokerGeneration
data LifecycleCursor scope planId frame brokerGeneration verb phase
```

The hidden kernel additionally owns
`IndexedPlanSnapshot scope specDigest planId configId`. `ProjectPlan` retains that companion; the
snapshot leaf and restricted trusted Mode importer consume it. It is absent from the public facade; `StablePlanSnapshot` is its index-erased,
non-authorizing byte projection.

The static project specification remains independent of lifecycle scope and every generative identity.
`HostBootstrap.CLI` passes its static service registry, rank-2 plan builder, and rank-2 forward-child
projector (`psForwardChildPlan`; the bare binary passes `refuseForwardChildPlan`) to the lower component
finalizer; the test-config family remains solely on `ProjectSpec cfg tcfg`. Scope finalization reuses the
service-registry continuation and retains the exact codec, services, identity-parametric builder, and
forward-child projector in one wrapper:

The finalized wrapper produces a non-empty stream in the exact root, scope, specification, and configuration
admitted by the plan constructor. Because authored fragments may depend on the admitted configuration, this
projection validates the concrete stream and reports an empty or invalid result at that boundary:

```haskell

```

The plan facade also owns resource lookup. Reconciliation supplies only the closed resource family and stable
operation key; the plan supplies the generative resource and frame indices:

```haskell
data PlannedResourceKind resource

withPlannedResourceOfKind
  :: ProjectPlan scope specDigest planId configId cfg

  -> OperationKey

```

Plan-owned edge and guest-alias projections are derived through the same facade. A `PlannedStep` exposes only
its own resource and declared dependency prefix, so an action cannot perform whole-plan lookup.

Context admission is a pure check of descriptive data. It checks the declared topology and current-frame term
before generating the frame phantom and jointly yields the plan-local frame, project-frame, and
validated-context evidence so callers cannot select one index independently:

```haskell
withCurrentFrame
  :: ProjectCfg cfg
  => ProjectPlan scope specDigest planId configId cfg
  -> BinaryContext
  -> (forall frame.
        CurrentFrame scope planId frame
        -> ProjectFrame scope specDigest planId configId frame
        -> ValidatedContext scope planId frame
        -> a)
  -> Either FrameError a
```

`CurrentFrame`, `ProjectFrame`, and `ValidatedContext` carry no command, journal, or mutation authority. The
effectful lifecycle opener and command-authority gate consume them later with independent root and lease
evidence.

Fresh persistence runs one serialized protected sequence. It stores, flushes, reads back, and verifies the
private indexed snapshot in one protected entry. After leaving that entry, a separate fresh-only lease
compare-and-swap binds the run-lease record to the resulting digest. The two durable transitions are ordered;
they are not an atomic multi-record transaction. Only completion of the whole sequence yields the matching
evidence package:

```haskell
withPersistedPlanSnapshot
  :: RootInvocationAuthority scope brokerGeneration VerbUp
  -> UnboundRunLease scope brokerGeneration
  -> ProjectPlan scope specDigest planId configId cfg
  -> (forall planDigest.
        VerifiedPlanSnapshot scope specDigest planDigest
        -> BoundPlanSnapshot scope specDigest planDigest planId
        -> PlanDigestBinding scope specDigest planDigest planId
        -> BoundRunLease scope specDigest planDigest brokerGeneration
        -> NormalActiveRecovery
             scope specDigest planDigest planId brokerGeneration
        -> IO a)
  -> IO (Either SnapshotError a)
```

Protected admission of an existing Production invocation starts from only the protected store and installed
project identity. It opens the exact Production mode/root, already-bound lease, and immutable verified
snapshot itself. A terminal acknowledgment receives only its stable close key and generates no local plan.
Only the Open branch generates one local `planId` and yields the fully indexed evidence binding that identity
to the persisted digest and broker generation:


The public `BoundInvocationRecovery` constructor is hidden and its indices are nominal. Its hidden
representation retains the already classified Open revision; the scope-only durable observation used to
reach that branch stays package-private and cannot be passed as plan evidence.

### Sprint 12.1: Step identity and node-definition validation [Done]

**Status**: Done
**Implementation**: `core/hostbootstrap-core/internal/handoff-implementation/HostBootstrap/Step.hs`,
`core/hostbootstrap-core/test/StepSpec.hs`
**Substrates**: linux-cpu
**Docs to update**: `documents/architecture/composition_methodology.md`

#### Objective

Define a closed core identity vocabulary, a disjoint project identity namespace, and the structural rules an
authored node must satisfy.

#### Deliverables

- `CoreStepId` is closed and `ProjectStepId` is validated, so core and project identities are disjoint.
- `StepFrame` carries a semantic identity and a presentation label; validation rejects inconsistent labels.
- Each node declares its dependencies, frame, stable operation key, implementation revision, reverse-adapter
  revision, and reverse policy together. Every constructor starts both revisions at 1, and attaching a reverse
  effect with `reversedBy` leaves an already declared reverse-adapter revision unchanged.
- Each frame with a successor declares exactly one descent, and the innermost frame declares none.
- A node declares at most one reverse effect (`DuplicateStepReverse`), and a preserved node declares none
  (`ReverseOnPreservedStep`). A project-managed node that declares none is legal: its reverse records
  `TeardownForeignRetained` ("the node acquired nothing this frame must release"), which the demo's direct
  host-provider `deployVMStep` relies on. A core-managed node without a callback may use its core adapter.
- Root-sensitive fragments are rank-2 in `CanonicalProjectRoot`, so authored paths arise from admitted root
  authority.

#### Validation

`StepSpec` covers identity disjointness and the four exact invalid project identities, empty frame and
label payloads, inconsistent frame labels, descent structure and unknown post-handoff frames, stable
operation keys, `ReverseOnPreservedStep` and `DuplicateStepReverse`. The suffix control requires
`PostHandoffBeforeDescentComplete 2`. The constructor control checks both initial revision readers for
all ten core smart constructors and a project step. Revision-order controls check both arrangements of
`reverseAdapterAt` and `reversedBy`, and explicit replacement through `reversedByAt`. The no-callback
project-managed provider plan is admitted. The sprint closes after those cases and the complete host
static gate pass.

The `project step identities` group requires `projectStepId ""` to return exactly
`Left "project step identity must not be empty"`; its path-separator, namespace-separator and
non-ASCII cases use `a/b`, `a:b` and `é`, each requiring the exact stable-token refusal with the shown
raw value. "An empty frame identity reports its exact step position" requires `EmptyFrameId 1`,
"an empty step label reports its exact step position" requires `EmptyStepLabel 1`, and the undeclared
post-handoff case requires `PostHandoffForUnknownFrame 2 "vm-orchestrator-1"`.
"Attaching a reverse effect preserves an already declared adapter revision" requires both orderings
to retain revision three; the explicit replacement case requires revision five. "A project-managed
node may declare no reverse effect" admits the actual `deployVMStep` plan with no callback.

### Sprint 12.2: Plan-independent step observations [Done]

#### Objective

Represent what a node observes without granting ownership or plan authority to its action.

#### Deliverables

- A node action returns `StepObservation`, and the interpreter turns that observation into its structured
  reconciliation row.
- The observation carries no managed handle, receipt, scope, or plan index.
- Target-state, conflict, safety-refusal, and unsupported outcomes remain distinct and name their node.
- The interpreter publishes the durable unknown phase before the external effect and settles in a fresh
  protected entry after the effect.
- A safety refusal and a caught synchronous callback exception settle terminally; the latter closes the
  session before rethrowing its original exception. Interrupted or unresolved work retains durable unknown
  state for recovery.
- Each invocation uses its freshly allocated broker generation in the operation-session identity.

#### Validation

`StepSpec` covers the observation vocabulary. `ChainSpec` covers result conversion, fail-closed dependency
ordering, the durable protected sequence, terminal settlement, and unknown-state retention.

uses `tryProtectedEntry` inside the actual effect. Contention produces the exact held-entry assertion

and store errors also fail immediately. The callback captures
actual durable phases, and the case requires exactly `EffectOutcomeUnknown` afterwards, so a missing
callback or wrong/absent record cannot satisfy it. Observation-row execution is covered by ChainSpec's
`observationCases`; StepSpec covers the plan-independent vocabulary.

### Sprint 12.3: Projected-operation declarations [Done]

**Status**: Done
**Implementation**: `core/hostbootstrap-core/internal/handoff-implementation/HostBootstrap/Step.hs`,
`core/hostbootstrap-core/internal/handoff-implementation/HostBootstrap/Lifecycle/Execution.hs`,
`core/hostbootstrap-core/src/HostBootstrap/Chain.hs`,
`core/hostbootstrap-core/test/StepSpec.hs`
**Substrates**: linux-cpu
**Docs to update**: `documents/architecture/composition_methodology.md`

#### Objective

Let a node act through operation keys that its own validated definition projects.

#### Deliverables

- A projected key names an ordered dependency prefix, the declaring node, and a non-empty suffix.
- Every operation key is a sequence of `/`-free segments: the free-text payloads of `EnsureToolId` and
  `PostHandoffId` are validated like `projectStepId` (non-empty, no `/` or `:`), so the projection scan
  consumes each dependency key unambiguously.
- A projected key is unique across the graph and disjoint from every node's primary operation key.
- The interpreter registers a node and all its declared projections in one protected entry.
- A node action can take its primary gate and each declared projection gate at most once.
- A projection outside the node's declaration is unavailable to the action.
- Session close refuses a declared projection whose action leaves it unsettled.

#### Validation

`StepSpec` "a core tool name cannot extend another operation key" requires the exact
`InvalidCoreStepName (CoreStepIdentity (EnsureToolId "z/core:copy-source"))` refusal. Its named-core cases
also cover empty tool and post-handoff names, a valid `ghc` name, the existing ASCII token alphabet for
both constructors, and earlier frame/label refusal precedence. "a suffixed tool name cannot impersonate
its valid projected operation" first admits the valid declared projection, then refuses the conflicting
tool name at the name boundary.

The `StepAction` Haddock and composition guide describe the descriptor's nominal indices and the
unindexed gate's runtime plan/session match in `acknowledgeOutcome`, followed by its live permit,
open-session, fence, journal-version and durable-record checks.

`ChainSpec` "an action takes the gate for an operation its node projects", "the descriptor names exactly
the projections the plan validated", "a node's own gate is reachable from its action", "a projection
registers and settles with its node", and "a declared projection the node never takes leaves the session
unable to close" exercise the existing interpreter contract.

#### Objective

- It re-reads the bound run lease and refuses when the lease is absent, unbound, or at another record version
